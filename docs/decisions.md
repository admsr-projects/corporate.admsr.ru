# Журнал архитектурных решений (ADR)

Фиксируются только **подтверждённые** решения: те, что видны в коде, конфигурации,
комментариях, README или аудите. Если причина решения нигде не зафиксирована —
так и написано, домыслы не добавляются.

Формат записи: контекст → решение → подтверждение → следствия.

---

## ADR-001. Параллельная миграция PHP → Go с сохранением URL `/api/*.php`

- **Статус:** действует
- **Решение:** новый backend пишется на Go, но URL-контракты `/api/<имя>.php`
  не меняются. Переключение — точным allowlist'ом nginx
  (`location = /api/<файл>.php` имеет приоритет над регуляркой PHP).
- **Подтверждение:** `backend/README.md` («Vue SPA без изменений… nginx
  переключает маршруты точным allowlist»), `deploy/nginx-corporate.admsr.ru.conf:55-56`,
  `backend/cmd/api/main.go`.
- **Причина (подтверждена):** не менять фронтенд при переносе backend.
- **Следствия:** три списка путей (Go mux, nginx, Vite proxy) нужно держать
  синхронными; для многих эндпоинтов существуют две реализации.
- **Правило переноса, зафиксированное в `backend/README.md`:**
  handler → smoke → nginx allowlist → наблюдение → удаление PHP только после стабилизации.

## ADR-002. PHP-слой заморожен; правки backend — только в Go

- **Статус:** действует с 2026-09-21
- **Решение:** `api/` не изменяется; киоск (`src/pages/Kiosk/`, `AppKiosk`) не
  трогаем. Уже внесённые точечные правки в PHP оставлены как есть.
- **Подтверждение:** `docs/PROJECT_AUDIT.md`, §8 «Решение владельца (2026-09-21)».
- **Следствия:** проблемы SEC-002…SEC-005 остаются открытыми осознанно;
  новая функциональность backend пишется только на Go.

## ADR-003. Личность пользователя берётся только из серверной сессии

- **Статус:** действует
- **Решение:** ни `userId` из тела запроса, ни заголовок `X-User-Id` не являются
  источником личности. Только `auth.Service.CurrentUser` по токену сессии.
- **Подтверждение:** `backend/internal/auth/session.go:159-201`;
  `tests_routes.go` (`viewer()`); `forms.go` (`formsRequireUser`/`formsRequireEditor`);
  `PROJECT_AUDIT.md`, SEC-006/007/008.
- **Причина (подтверждена):** клиентские идентификаторы подделываются — это
  приводило к полному обходу авторизации.
- **Следствия:** клиентский код, всё ещё отправляющий `userId`, — рудимент
  (см. [known-issues.md](known-issues.md), IMP-13). `owner_id IS NULL`
  трактуется как «доступ запрещён».

## ADR-004. Двухканальная передача токена: cookie + Bearer

- **Статус:** действует
- **Решение:** при входе выдаются одновременно httpOnly-cookie `corp_session` и
  `sessionToken` в теле. Сервер принимает `Authorization: Bearer` →
  `X-Session-Token` → cookie в этом порядке.
- **Подтверждение:** `backend/internal/auth/session.go:60-73,108-126`;
  `src/composables/useAuthSession.ts`.
- **Причина (подтверждена частично):** комментарий в `useAuthSession.ts:1-4` —
  «Используется модулем курсов; не ломает legacy API, которые ещё принимают
  userId». То есть Bearer вводился под модуль курсов, cookie осталась для
  легаси-вызовов. Почему не унифицировали позже — **[НЕИЗВЕСТНО]**.

## ADR-005. Проверка прав внутри хендлеров, без middleware

- **Статус:** действует
- **Решение:** `mux.Handle(path, handler)` без цепочек; guard
  (`requireUser`/`requireAdmin`/`requireSection`) вызывается первой строкой
  каждого метода.
- **Подтверждение:** `backend/cmd/api/main.go`, `backend/internal/handlers/section.go`.
- **Причина:** **[НЕИЗВЕСТНО]** — в коде не зафиксирована.
- **Следствия:** забыть guard легко; именно так возникли SEC-001/009. Отсюда
  требование покрывать новые эндпоинты тестом вида
  «аноним → 401 до обращения к БД» (`auth_guards_test.go`).

## ADR-006. Права по разделам через группы портала, плюс суперадмин

- **Статус:** действует
- **Решение:** два независимых уровня — `user_info.user_group = 'admin'`
  (всё) и членство в `portal_access_groups` с правами на `section_key`.
  Для курсов — дополнительное сужение по категории.
- **Подтверждение:** `db/migration/V5`, `V6`; `backend/internal/auth/permissions.go`;
  `src/composables/useSectionAccess.ts`.
- **Следствия:** список секций продублирован во фронте и в Go; синхронизация ручная.

## ADR-007. UI-тоггл роли отделён от прав

- **Статус:** действует
- **Решение:** `localStorage['ui-role']` переключает отображение админ-функций.
  Для суперадмина `canEdit` требует `currentRole === 'admin'`; на права
  обычного пользователя тоггл не влияет.
- **Подтверждение:** `src/stores/role.js`, `src/composables/useSectionAccess.ts:110-118`,
  `src/components/AppHeader.vue:48-58`, `src/router/index.js:280-286`.
- **Причина (выводится из кода):** возможность посмотреть портал глазами
  сотрудника. Явной формулировки в коде нет — **[ЧАСТИЧНО]**.
- **Следствия:** роль в localStorage не является защитой; сервер её не читает.

## ADR-008. Киоск работает без авторизации и без админ-функций

- **Статус:** действует
- **Решение:** ветка `/kiosk` доступна анонимно; роль принудительно `user`;
  `requiresAdmin`/`requiresSection` внутри киоска → редирект на `/kiosk`;
  переходы на «обычные» маршруты из киоска перенаправляются на киоск-аналоги
  **до** проверки авторизации.
- **Подтверждение:** `src/router/index.js:243-277`, комментарий в коде:
  «киоск работает полностью без входа».

## ADR-009. Тема как набор CSS-переменных, применяемых из JS

- **Статус:** действует
- **Решение:** полные палитры Tailwind объявлены в `:root`
  (`src/assets/tailwind.css`), а `applyUiTheme()` копирует выбранную палитру в
  переменные Nuxt UI (`--ui-color-primary-*`, `--ui-color-neutral-*`, `--ui-primary`)
  и задаёт `--font-sans`, `--ui-radius`, `data-ui-font`.
- **Подтверждение:** `src/composables/useUiTheme.ts:186-224`; комментарий там же:
  «Tailwind v4 exposes palette steps as CSS vars… We mirror them into Nuxt UI vars».
- **Причина (подтверждена комментарием в CSS):** палитры объявлены как `:root`,
  «so they are never tree-shaken by Tailwind».
- **Следствия:** доступны 18 primary и 9 neutral цветов, 4 шрифта, 5 радиусов;
  тема применяется до монтирования приложения (`src/main.js`), чтобы не было
  мигания.

## ADR-019. Миграции идемпотентны, без таблицы версий

- **Статус:** действует
- **Решение:** весь SQL пишется как `IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`;
  `deploy.sh` прогоняет **все** `V*.sql` при каждом деплое.
- **Подтверждение:** `deploy/deploy.sh:247-259`, текст миграций.

## ADR-020. Недействительная сессия → единый выход, а не ошибка в интерфейсе

- **Статус:** действует с коммита `bcd9d95` (2026-09-22)
- **Решение:** если авторизованный запрос вернул 401 и повторная выдача токена
  не помогла, приложение один раз уводит пользователя на `/login` с пометкой
  «Сессия истекла», вместо того чтобы показывать ошибку на каждом запросе.
- **Подтверждение:** `src/composables/useAuthSession.ts:64-93,186-191,209-221`
  (комментарий: «Это убирает повторяющуюся ошибку „Требуется авторизация“:
  вместо неё пользователь один раз чисто уводится на страницу входа»);
  `src/composables/useSessionActivity.ts:57-61`; `src/pages/login.vue:28-34`.
- **Причина (подтверждена комментарием):** UX-001 — при истёкшей сессии
  интерфейс выглядел залогиненным и сыпал ошибками.
- **Связанное решение того же коммита:** TTL сессии сделан **скользящим** —
  `CurrentUser` при каждом авторизованном запросе сдвигает `expires_at` на
  полный TTL (`backend/internal/auth/session.go:194-205`). Причина
  (подтверждена комментарием): активный пользователь не должен «отваливаться»
  посреди работы, а реально простоявшая сессия истекает честно.
- **Следствия:** обработчик регистрируется один раз при старте
  (`startSessionActivity`); повторные срабатывания подавляются флагом
  `unauthorizedFired` (сброс через 5 с). Остаток: `check-auth.php` всё ещё
  проверяет флаг `auth`, а не токен.

## ADR-021. «Управление обучением» — отдельная страница, а не вкладка

## ADR-022. Разделители и рамки на `bg-elevated` — `*-accented`

- **Статус:** действует с 2026-09-22
- **Решение:** внутри карточек и панелей с фоном `bg-elevated` рамки и
  разделители — `border-accented` / `ring-accented`, не `*-default`.
- **Подтверждение:** `node_modules/@nuxt/ui/dist/runtime/index.css` — в тёмной
  теме `--ui-bg-elevated` и `--ui-border` оба равны `neutral-800`, а
  `--ui-border-accented` — `neutral-700`.
- **Причина (подтверждена):** `border-default` на `bg-elevated` в тёмной теме
  совпадает с фоном — разделитель невидим (замечено владельцем).
- **Следствия:** на фоне страницы (`bg-default`) `*-default` по-прежнему
  годится. Hover-подсветка внутри `bg-elevated` — `bg-accented/40`, а не
  `bg-elevated/…` (иначе эффекта нет).

## ADR-023. Мастер создания курса — сквозные «Шаг N из 4»

- **Статус:** действует с 2026-09-22
- **Решение:** создание курса (1) → тема (2) → материал (3) → тест темы (4);
  баннеры и тосты между шагами используют одну нумерацию. Флаг режима — `?guide=1`.
- **Подтверждение:** `CourseCreatePage.vue`, `TopicFormPage.vue`,

  участвовал, но его тост говорил «Шаг 1», и следующий экран встречал вторым
  «Шагом 1 из 3».

## ADR-024. Засчёт времени: файлы и ссылки — без требования фокуса

- **Статус:** действует с 2026-09-24
- **Решение:** heartbeat для `rich_text` идёт, только если вкладка портала
  активна и было действие за 30 с; для файлов и ссылок — пока материал открыт
  и вкладка портала не закрыта.
- **Подтверждение:** `shouldBeat()` в `src/pages/Courses/employee/CourseMaterialPage.vue` (до ADR-034 — `CourseTopicPage.vue`).
- **Причина (подтверждена владельцем):** файлы и ссылки открываются в новой
  вкладке; при требовании фокуса время на них не шло вовсе, и материал с
  минимальным временем нельзя было пройти, читая его (IMP-20).
- **Следствия:** защита от накрутки — только серверная: `MaterialHeartbeat`
  не засчитывает паузы длиннее 90 с и не добавляет больше 60 с за раз.

## ADR-025. `NextAction` сам завершает «созревшие» темы и не обрывается на просрочке

- **Статус:** действует с 2026-09-24
- **Решение:** (1) если условия темы выполнены, а статус не `completed`,
  `NextAction` завершает тему, пересчитывает блокировки и вычисляет шаг заново;
  то же делает `MaterialHeartbeat` после каждого засчитанного интервала.
  (2) Для `overdue` вычисляется реальный следующий шаг.
- **Подтверждение:** `markTopicCompleted`, `CompleteTopicIfReady`, `NextAction`
  в `backend/internal/courses/common.go`; `MaterialHeartbeat` в
  `backend/internal/handlers/courses.go`.
- **Причина (подтверждена владельцем):** IMP-18, IMP-19 — сотрудник упирался в
  тупик и не мог пройти курс.
- **Следствия:** `NextAction` — чтение **с побочным эффектом** (как и раньше:
  он уже вызывал `RecalculateLocks`). Рекурсия ограничена числом тем:
  повторный вызов происходит, только если `UPDATE` реально изменил строку.

## ADR-026. Порядок тем — перетаскиванием на `vuedraggable`

  `i-lucide-grip-vertical`; стрелки остались в меню `⋯` для клавиатуры и тача.

## ADR-027. Адаптивность шапки — container queries, а не брейкпоинты окна

- **Статус:** действует с 2026-09-24
- **Решение:** корень шапки помечен `@container`; вариант кнопки поиска
  выбирается по ширине шапки (`@4xl` = 56rem, `@6xl` = 72rem): иконка →
  «Поиск…» → полная подпись.

## ADR-032. Данные сотрудника — один источник: `user_info`

- **Статус:** действует с 2026-09-28
- **Решение:**
  - журнал отсутствия получает ФИО, ОФО и должность с сервера из `user_info`
    (POST игнорирует их в теле) и показывает текущие данные сотрудника
    (`absenceView` в `backend/internal/handlers/absence.go`); копия в записи —
    на случай, если сотрудника уже нет;
  - подразделения везде — дерево `ofo_unit`; журнал больше не читает легаси `ofo.php`;
  - ОФО и должность заполняются одним компонентом `UserWorkFields.vue` в
    профиле, онбординге и админке;
  - имя — `userFullName` / `userShortName` (`src/utils/userName.ts`);
  - профиль не хранит копию имени и аватара в `localStorage`.
- **Причина:** по жалобе владельца на расхождения. Найдено: журнал брал
  ФИО/ОФО/должность из снимка `auth-user` на момент входа (после правки профиля
  расходились, а сотрудник мог прислать любые значения); подписи ОФО журнала
  шли из таблицы `ofo`, а `user_info.ofo` ссылается на `ofo_unit`; в админке
  ОФО вводили номером, а должность — текстом; при открытии профиля должность,
  которой нет в справочнике, стиралась; шапка при пустой должности показывала
  `user`/`admin` или «Инженер»; копия аватара в `localStorage` переходила к
  следующему пользователю браузера.
- **Следствия:** если сотрудника перевели, его прошлые отсутствия показываются
  с новым ОФО и попадают в фильтр нового подразделения. Отметить отсутствие без
  ОФО и должности в профиле нельзя (422 с подсказкой).

## ADR-033. Реакции на новости — на сервере, по сотруднику

- **Статус:** действует с 2026-09-28
- **Решение:** таблица `news_reactions (news_id, user_id, reaction)` (V11), PK по
  тройке — одна реакция каждого вида на сотрудника, несколько разных можно.
  8 реакций, список в коде (без CHECK — добавление не требует миграции).
  Поставить/снять — `POST news.php?id=…&action=react {reaction, active}` только
  с сессией; кто отреагировал — `GET …&action=reactors&reaction=…` (для вошедших).
  Старый `action=like` оставлен как синоним реакции «like».
- **Причина:** задача владельца «реализовать систему реакций полностью». Было:
  лайк — анонимный счётчик `news.likes` без входа, отметка «я лайкнул» — в
  `localStorage` (с другого браузера лайк ставился повторно, «снять» уменьшало
  чужие), ❤️ и 🙂 показывали заглушку.
- **Следствия:** `news.likes` больше не меняется и прибавляется к счётчику «like»
  как накопленные до реакций анонимные лайки — иначе на проде обнулились бы
  существующие цифры; снять их нельзя. В киоске реакции не показываются
  (как и раньше лайк).

## ADR-034. Материал курса — на своей странице, файлы показываются встроенно

- **Статус:** действует с 2026-09-28
- **Решение:** маршрут `course-material`
  (`/courses/:enrollmentId/topics/:topicId/materials/:materialId`,
  `src/pages/Courses/employee/CourseMaterialPage.vue`); страница темы стала
  оглавлением. PDF — `<iframe>` со встроенным просмотрщиком браузера, видео —
  `<video>`, изображения — `<img>`; прочие файлы — «Скачать». Вид определяется по
  MIME, при его отсутствии — по расширению (`courseMaterialView.ts`). Heartbeat
  переехал на страницу материала; правило ADR-024 сохранено.
  С 2026-09-29 переход к следующему шагу из курса или после теста ведёт на
  страницу темы, а не сразу в материал (просьба владельца).
- **Причина:** задача владельца: «просмотр PDF и видео прямо на странице с
  материалами; один материал — одна страница». Раньше все материалы темы были на
  одной странице, файлы открывались в новой вкладке.
- **Следствия:** PDF показывает сам браузер — в Chrome/Edge/Firefox/Яндекс на
  компьютере работает; где просмотрщика нет (`navigator.pdfViewerEnabled ===
  false`, напр. Android) — вместо фрейма кнопки «Открыть»/«Скачать». Единый вид на
  всех устройствах дала бы pdf.js — это новая зависимость, не вводилась.
  Файлы отдаются по cookie сессии (фрейм и плеер не шлют `Authorization`).

## ADR-036. Назначения на ОФО и «всем» — постоянные

- **Статус:** действует с 2026-09-28
- **Решение:** цель `all` (V12) и досоздание записей по действующим назначениям
  `ofo`/`all` опубликованных версий — `courses.Service.SyncStandingAssignments`
  (`backend/internal/courses/assign.go`), вызывается при входе (`auth.go`),
  сохранении профиля (`profile.go`) и в `courses_for_me`. Ранее отменённая
  администратором запись по тому же назначению не восстанавливается. Срок «N дней»
  хранится в назначении (`deadline_days`) и считается от момента выдачи.

  публикации (отмены назначения целиком в интерфейсе нет). Назначение на
  пользователя по-прежнему разовое. Без миграции V12 «всем» отвечает 503.

## ADR-037. «Назад» в тесте есть всегда, пропущенный вопрос не фиксируется

- **Статус:** действует с 2026-09-29
- **Решение:** `src/pages/Tests/TestRunner.vue` (общий для тестов курса и
  модуля `/tests`): кнопка «Назад» показывается всегда (кроме истёкшего
  времени и подсветки ответа); «Далее» фиксирует только **данный** ответ —
  пропущенный вопрос остаётся открытым. Менять данные ответы при возврате можно
  только с «Разрешить изменять ответ» (`allowChangeAnswer`), иначе вопрос
  показывается как «Ответ зафиксирован» с кнопкой «Дальше». Настройка
  «Свободный переход между вопросами» (`freeNavigation`) больше ни на что не
  влияет и убрана из конструкторов; в конструкторе теста курса на её месте —
  «Разрешить менять ответы до завершения». Поле в БД и API осталось.
- **Причина:** баг-репорт владельца 2026-09-29: «есть кнопка далее, но нет
  назад»; «завершил тест, не ответив на все вопросы, — возвращает к вопросам,
  но ответить нельзя». Второе — дефект: `lockCurrentIfNeeded` фиксировал
  вопрос при «Далее» без ответа.
- **Следствия:** у форм модуля `/tests`, где «Свободный переход» был выключен,
  тоже появился «Назад» (только просмотр данных ответов).

- **Решение:** между аватаром и итогом добавлен компактный шаг «Внешний вид» (`OnboardingPage.vue`): строка

- **Причина:** просьба владельца 2026-09-29: рассказать про настройку темы и предложить пользователю самому настроить

## ADR-039. Типы вопросов «Соответствие» и «Классификация»

- **Статус:** действует с 2026-09-29
- **Решение:** `match` (понятие → определение) и `classify` (утверждение → категория) — один вопрос, у которого
  каждому элементу слева выбирается один вариант справа. Хранение в `test_options` с `role` и `target_option_id`
  (V13), ответ — JSON `{itemId: targetId}` в `test_answers.text_value`; ключ клиенту — `correct: {itemId: targetId}`.
  Оценка: один вопрос — один балл, засчитывается только если верны все соответствия (`tests.ScorePairing`; сначала
  считали по парам, владелец 2026-09-30 потребовал «один вопрос — один балл»). У `match` определения на клиенте
  всегда перемешиваются, допустимы лишние определения. Прохождение — перетаскиванием карточек (`vuedraggable`, уже
  в зависимостях): `match` — определение в ячейку понятия (в ячейке одно, прежнее возвращается к остальным),
  `classify` — утверждение в колонку категории; нажатие на разложенную карточку возвращает её.
  **С клавиатуры (с 2026-10-01, IMP-60):** Enter/Пробел на карточке из общего набора выбирает её, затем кнопка
  «Положить сюда» в нужной ячейке или колонке (она появляется только при выбранной карточке); Enter/Пробел на
  разложенной карточке возвращает её. Фокус после действия переходит на карточку на новом месте, выбор объявляется
  через `aria-live`. Выбор карточки мышью не включён — мышь и касание работают только перетаскиванием, как раньше.
  Код: `backend/internal/tests/pairing.go`, `common.go` (загрузка, сохранение, оценка), `handlers/tests_routes.go`,
  `attempt_review.go`; фронтенд — `questionTypes.ts`, `PairingEditor.vue`, `TestRunner.vue`.
- **Причина:** просьба владельца 2026-09-29: в `Тест.docx` курса по ИИ есть задания «Соотнесите понятия с
  определениями» и «Классифицируйте полученные ответы», которых в модуле не было (раньше их пришлось разбирать на
  отдельные вопросы с одним вариантом).
- **Следствия:** нужна миграция V13, иначе сохранение формы с новым типом упрётся в CHECK. Тесты второго модуля
  (`/kiosk/tests`, `src/tests/`, `forms*.php`) новые типы не получили. «Соответствие» доступно только в тесте.

## ADR-040. Профиль — «стена ВКонтакте» на сервере

- **Статус:** действует с 2026-10-01
- **Решение:** профиль сотрудника в компоновке старого ВКонтакте, но на семантических токенах портала (цвета,
  шрифт, скругление следуют за темой): слева аватар, действия, «Коллеги» (активные сотрудники того же
  подразделения, 6 штук); справа ФИО, анкета, «Информация» («О себе», «Интересы»), стена. `/profile/:id` —
  профиль коллеги, вход в него — из поиска портала, «Коллег» и имени автора записи.
  Стена на сервере (`profile_wall.php`, V14): писать может любой вошедший сотрудник на любую стену, править —
  только автор, удалять — автор, владелец стены или администратор. Запись — **простой текст** до 4000 символов,
  выводится как текст (`whitespace-pre-line`, без `v-html`): HTML пользователей сервер не хранит, санитайзер
  не нужен. Реакции — те же ключи и компонент, что у новостей (`NewsReactions` с `target="wall"`,
  `wall_post_reactions`). День рождения — из xlsx дней рождения по ФИО (только день и месяц), отдельного поля нет.
  Редактирование — `USlideover` (`ProfileEditSlideover.vue`); настройка темы из профиля убрана — она есть в
  меню шапки.
  Код: `backend/internal/handlers/profile_wall.go`, `profile.go` (`?view=page`), `birthdays.go` (`BirthdayOf`);
  `src/pages/ProfilePage.vue`, `src/components/profile/*`, `src/composables/useProfileWall.ts`.
- **Причина:** просьба владельца 2026-10-01: профиль не нравился, прокрутка была сломана (у `UMain` не было
  `overflow-y-auto`), стена жила только в `localStorage` автора (IMP-03); «хочу, чтобы профиль был как старая
  стена ВКонтакте». Ответы владельца: писать может любой коллега; у записей — реакции как у новостей (без
  комментариев и фото); компоновка VK на токенах портала; в анкете — должность, ОФО, контакты, день рождения,
  «О себе» и интересы.
- **Следствия:** нужна миграция V14, без неё стена отвечает 503 с понятным текстом, а страница профиля
  открывается без «О себе». Форматирование (жирный, списки, эмодзи-меню) из прежнего редактора поста
  ушло — `UEditor` для стены удалён вместе с `wallEditorExtensions.ts` / `wallEditorToolbar.ts`. Записи из
  `localStorage` не переносились. Комментариев и фото в записях нет — это отдельная задача.

## ADR-041. Профиль: данные из учётной записи не редактируются, добавлены желания, награды, курсы, отсутствия

- **Статус:** действует с 2026-10-01
- **Решение:** на портале нельзя менять ФИО, телефон, электронную почту, ОФО и должность. `POST profile.php` пишет
  только `avatar_url`, `about`, `interests` и — **один раз** — `ofo` и `role`: ОФО принимается, пока оно не задано
  (пусто, `-1`, не положительное число), должность — пока пуста или пока не задано ОФО (`planWorkFields`,
  `backend/internal/handlers/profile.go`, тест `profile_test.go`). Остальное сервер молча игнорирует — не 403,
  чтобы онбординг, который шлёт всю карточку, не ломался. Это же закрывает IMP-57: поля, которых нет в теле, не
  затираются. Онбординг блокирует выбор ОФО, если оно уже задано (`UserWorkFields.ofoLocked`). Админка
  (`users.php`) по-прежнему правит всё — исправить ошибку в данных сотрудника может только администратор.
  В профиль добавлены: «Желания» (`profile_wishes`, пишет сам сотрудник, до 20 штук по 200 символов), «Награды»
  (грамоты и достижения, `profile_awards`, выдаёт и удаляет администратор), «Пройденные курсы» (завершённые
  назначения из `course_enrollments`, видят все вошедшие). Блок «Журнал отсутствия» (последние 5 записей)
  в профиле был, но **убран на фронтенде по просьбе владельца 2026-10-05**: журнал живёт на своей странице.
  Сервер всё ещё отдаёт `absences` в ответе `profile.php`, фронтенд поле не читает. Код: `profile.go`
  (`addPageSections`), `profile_extras.go`, `src/components/profile/*`.
- **Причина:** просьба владельца 2026-10-01: «редактировать ФИО, телефон, ОФО, должность, электронную почту на
  корп портале нельзя будет»; в профиле должны быть пройденные обучения и пожелания. Ответы владельца: «пожелания» —
  список желаний сотрудника (как у ВКонтакте); показывать пройденные курсы, журнал отсутствия и «грамоты и
  достижения»; ОФО и должность — один раз при первом входе. Откуда берутся ФИО, телефон и почта после создания
  учётки — **[НЕИЗВЕСТНО]**: `sync.go` только создаёт запись (`ON CONFLICT DO NOTHING`) и обновлять потом не
  умеет, так что менять их теперь может только администратор.
- **Следствия:** нужна миграция V15 (без неё желания и награды отвечают 503, профиль открывается пустыми блоками).
  Награды — только текст (без картинки грамоты); «Выдать награду» видит администратор в режиме «Администратор».
  Пройденные курсы видят все, у чужих без ссылки (назначение чужого не открыть). Сотрудник со ссылкой на уже
  заданное ОФО в онбординге его не меняет — только должность, если она пуста.

## ADR-042. Свой аватар: загрузка фото, квадрат 512×512

- **Статус:** действует с 2026-10-01
- **Решение:** сотрудник может загрузить свою фотографию (`POST /api/profile_avatar.php`, multipart, поле `avatar`).
  Только вошедший и только себе (личность из сессии). JPEG, PNG или WebP до 5 МБ; сервер обрезает по центру до
  квадрата 512×512, заливает прозрачность белым и пишет JPEG `<userID>-<hex>.jpg` в
  `<UPLOAD_DIR>/img/FullPic/avatars/uploads/` (URL `/img/FullPic/avatars/uploads/…`). Фото **сразу** становится
  аватаром (не ждёт «Сохранить»). Файл прежнего загруженного аватара удаляется — и при замене фото, и когда
  `profile.php` меняет аватар на готовый; удаляется только файл этого же пользователя в этой папке
  (`media.RemoveUploadedAvatar`, тест `avatar_test.go`). Свой аватар рисуется на всю рамку (`object-cover`),
  готовые стикеры — с полями (`object-contain`): `isUploadedAvatar()`. Готовые аватары остаются.
  Код: `backend/internal/handlers/profile_avatar.go`, `backend/internal/media/webp.go` (`SaveAvatar`),
  `src/components/profile/ProfileEditSlideover.vue`.
- **Причина:** просьба владельца 2026-10-01 — «добавить возможность загрузить аватар самостоятельно».
  Отдельный эндпоинт, а не `Upload/upload.php`, потому что тот открыт без входа (IMP-61) и режет картинку
  под галерею, не под аватар. Квадрат 512 — чтобы аватар был лёгким (≈10–60 КБ) и ровно ложился в круг и
  квадратные рамки.
- **Следствия:** `/img/FullPic/avatars/` теперь не только стикеры из `.gitignore`: подпапка `uploads/` пишется
  Go API, на сервере её отдаёт то же правило nginx, что и остальные `/img/`. Какой каталог у `/img/` на проде —
  по-прежнему DOC-05 **[НЕИЗВЕСТНО]**: если nginx берёт `/img/` из `public/img/`, а Go пишет в
  `UPLOAD_DIR`, фото не откроются — проверить так же, как загрузку в галерее. nginx: `client_max_body_size 7m`
  для этого пути. Обрезку нельзя настроить (всегда по центру), поворот по EXIF учитывается.

## ADR-044. Курсы: «Не сдан», любое подразделение при назначении, без «Полного описания»

- **Статус:** действует с 2026-10-02
- **Решение:** (1) когда итоговый тест не сдан и у формы включён лимит попыток, а попыток не осталось, Go
  переводит запись в `failed` (`FailIfFinalAttemptsExhausted`, вызывается после завершения попытки;
  `TryCompleteEnrollment` статус `failed` не трогает). Без лимита попытки не кончаются. Вернуть можно только
  «Обнулить результат». (2) Курс назначается на любое подразделение (`useOfoTree.unitItems`, путь «Корень / Отдел»),
  в результатах фильтр и подпись — по точному подразделению; «Включая вложенные» остаётся. (3) Поле
  `fullDescription` убрано из Go и фронтового типа.
- **Причина (подтверждена):** решения владельца 2026-10-02 по Q-08, Q-11, Q-09.
- **Следствия:** число попыток считается по форме и пользователю, как при старте попытки (`tests_routes.go`),
  поэтому «не сдан» наступает ровно тогда, когда старт новой попытки уже запрещён. Колонку
  `course_versions.full_description` не удаляли: её читает и пишет PHP (`api/` не трогаем) — снять её можно
  после отказа от PHP. На прод миграции не нужны. **Вживую не проверено** (только сборка, `go test`, чтение кода).

## ADR-049. Поздравление с днём рождения — запись на стене; колокольчик уведомлений без таймера

- **Статус:** действует с 2026-10-07
- **Решение:**
  - Поздравление — запись на стене именинника (`wall_posts`, V14) с отметкой `birthday_year` (V17):
    `profile_wall.php` `action=greet`. Сервер проверяет: не себе, именинник — активная учётная запись, его ФИО
    есть в xlsx дней рождения, сегодня — день рождения или до 3 дней после (с переходом через Новый год),
    одно поздравление от автора в год (уникальный индекс; повтор → 409). Свой текст до 4000 символов + 5 готовых
    фраз в коде (`BIRTHDAY_GREETING_TEMPLATES`), подставляются в поле и правятся.
  - Именинник из xlsx связывается с учётной записью по ФИО: `birthdays.php` отдаёт `userId` активного сотрудника;
    ФИО не нашлось или совпало у двух активных — `userId: null`, кнопки «Поздравить» нет.
  - Кнопка «Поздравить» — в виджете рабочего стола (группа «Сегодня») и в календаре; после отправки — «Вы
    поздравили» со ссылкой на стену. Вне окна у дня рождения в календаре — «Профиль».
  - Уведомления — общая таблица `notifications` (V17) и `notifications.php`; сейчас два вида: запись на вашей стене и
    поздравление. Колокольчик в шапке (`NotificationsBell.vue`) с числом непрочитанных, «Прочитать все», клик — на
    свою стену.
  - **Опроса по таймеру нет.** Список обновляется при открытии колокольчика, при переходах между страницами (не чаще
    раза в 30 с) и при возврате на вкладку.
  Код: `backend/internal/handlers/birthday_greetings.go`, `notifications.go`, `profile_wall.go`, `birthdays.go`
  (`buildUserIDMap`); `src/composables/useBirthdayGreetings.ts`, `useNotifications.ts`,
  `src/components/BirthdayGreetingSlideover.vue`, `NotificationsBell.vue`.
- **Причина (подтверждена):** просьба владельца 2026-10-07 «разработать функцию поздравления». Ответы владельца:
  поздравление — запись на стене; свой текст + шаблоны (шаблоны в коде, 5 фраз); поздравлять в день рождения и 3 дня
  после; один раз в год; ФИО без учётной записи — кнопку скрыть; имениннику сообщать колокольчиком, в нём же —
  записи на стене. Отказ от таймера — следствие кода: `auth.CurrentUser` при каждом авторизованном запросе обновляет
  `user_info.last_activity`, на которой держится выход по бездействию (`useSessionActivity`, 24 ч); опрос раз в минуту
  держал бы пользователя «активным» вечно.
- **Следствия:** нужна миграция V17 — без неё `greet` и `notifications.php` отвечают 503 с понятным текстом, обычные
  записи на стене публикуются (уведомление не создаётся, ошибка в логе). Новый эндпоинт `notifications.php` — в
  `main.go`, nginx wave2 и Vite; на сервере после деплоя нужен `reload nginx` (IMP-63). Окно 3 дня задано и во
  фронте (`BIRTHDAY_GREET_WINDOW_DAYS`), и в Go (`birthdayGreetWindowDays`) — менять парами. Новое уведомление
  появляется не мгновенно, а при следующем действии пользователя. Сопоставление по ФИО ломается на опечатках в xlsx
  (`ё`/`е` и пробелы нормализуются). «Сегодня» на сервере — по часовому поясу процесса Go; на сервере не проверялось.
  Не сделано (не заказывалось): поздравление в киоске, кнопка в профиле именинника, отметка «поздравление» на самой
  записи стены, уведомления о реакциях.

## ADR-050. Комментарии к новостям: два уровня, популярные сверху, лучший ответ в свёрнутой ветке

- **Статус:** действует с 2026-10-07
- **Решение:**
  - Комментарий к новости и ответы — таблица `news_comments` (V18). Два уровня, как во ВКонтакте: ответ на ответ
    попадает в ту же ветку (`root_id`) с пометкой «в ответ Имя» (`reply_to_id`, `reply_to_user_id`). Отвечать можно
    на любой комментарий, в том числе на свой.
  - Популярность — число всех реакций; при равенстве выше более новый. Реакции — те же 8 ключей
    (`news_comment_reactions`).
  - Комментарии — **только на странице новости** (под текстом): все комментарии, «Популярные» (по умолчанию) / «Новые», по 20 с «Показать ещё».
  - В ветке без «Развернуть» — самый популярный ответ; развёрнутая — все ответы по времени (так читается разговор).
  - Править — автор; удалять — автор, редактор раздела «Новости», админ. Комментарий с ответами удаляется мягко
    («Комментарий удалён», ответы живут); без ответов и ответы — физически; удалили последний ответ удалённого — уходит
    и он.
  - Ответ на ваш комментарий — уведомление `comment_reply` (`notifications.comment_id`); клик ведёт на
    `/news/:id?comment=<id>`, ветка закрепляется сверху развёрнутой.
  - В киоске комментариев нет (как и реакций); эндпоинт только для вошедших.
  Код: `backend/internal/handlers/news_comments.go`; `src/composables/useNewsComments.ts`, `src/components/news/*`.
  - **Изменено 2026-10-07 по просьбе владельца:** сначала под каждой карточкой ленты рабочего стола были 2 самых
    популярных комментария, «Все N комментариев» и поле ввода (превью пачкой `?newsIds=`). Владелец решил оставить
    комментарии только на странице новости — превью удалено целиком (компонент, загрузка пачкой, запрос в Go).
- **Причина (подтверждена):** просьба владельца 2026-10-07: «под новостью 2 самых популярных комментария и поле
  „прокомментировать“, реакции на комментарии, „ответить“, дерево, по умолчанию — самый популярный ответ, остальные по
  „развернуть“». Ответы владельца на вопросы: лента + страница новости; два уровня, как ВК; правка — автор, удаление —
  автор и редакторы новостей; в колокольчик — только ответы; на странице — популярные сверху с переключателем; при
  равенстве — более новый; отвечать себе можно. Порядок развёрнутой ветки по времени —
  решение исполнителя (не обсуждалось).
- **Следствия:** нужна V18 (после V17); без неё `news_comments.php` отвечает 503, а колокольчик — 503 «нужна V18»
  (запрос уведомлений читает `comment_id`). Новый эндпоинт — в `main.go`, nginx wave2, Vite; на сервере — `reload nginx`
  (IMP-63). `news_id` — soft ref: при удалении новости `news.go` удаляет её комментарии (реакции и уведомления уходят
  каскадом). Подсчёт популярности — подзапросом на каждый комментарий, без денормализованного счётчика: на текущих
  объёмах достаточно, на больших ветках может понадобиться. Нет: уведомлений автору новости и о реакциях, упоминаний
  `@`, вложений, комментариев в киоске и в сетке `/news` — не заказывалось.

## ADR-051. Цвет личных событий, «Изменить», напоминания накануне без планировщика

- **Статус:** действует с 2026-10-07
- **Решение:**
  - У личного события и встречи — цвет (`calendar_entries.color`, V19): «По умолчанию» (цвет по типу), 8 базовых
    цветов или любой из палитры (`UColorPicker`). Цвет красит точку на плашке, полосу и подложку карточки (рамка 30 %,
    фон 10 %, как у типов событий); текст — в цветах темы, чтобы читался в обеих схемах. Окраска — общие функции
    `calendarItemBarClass/Style`, `calendarItemSoftClass/Style` из `useCalendarFeed.ts`: страница календаря и виджет
    «Календарь» на рабочем столе красят событие одинаково (с 2026-10-08; до этого виджет красил только по типу).
  - В меню «⋮» — «Изменить» (та же форма, что при создании, вкл. цвет) и «Удалить»; `calendar_entries.php`
    `action=update`, только свои. Кнопки «Открыть» у личных событий нет (`actionLabel: ''`).
  - Напоминание накануне (`notifications`, `kind = 'event_reminder'`) о личных событиях и встречах и о мероприятиях, куда
    записались. **Планировщика нет:** напоминания создаёт `notifications.go` при каждом запросе уведомлений — то есть
    когда сотрудник открывает портал в день перед событием. Повторы исключает уникальный индекс по событию и дате;
    перенесли событие или отменили запись — напоминание удаляется. Клик ведёт на `/calendar?date=` (страница
    открывает этот день) или на страницу мероприятия.
  Код: `backend/internal/handlers/calendar_personal.go`, `notifications.go` (`generateReminders`, `sqlRemind*`);
  `src/components/EventColorPicker.vue`, `src/pages/CalendarPage.vue`, `src/composables/useCalendarFeed.ts`,
  `useNotifications.ts`, `NotificationsBell.vue`.
- **Причина (подтверждена):** просьба владельца 2026-10-07: «убери кнопки подробнее у личных событий, создай
  напоминания в уведомлениях за день до начала события, сделай выбор цвета (палитра + несколько базовых цветов)».
  Ответы владельца: напоминать о личных событиях и мероприятиях, куда записался; накануне, с утра; добавить
  «Изменить». Набор из 8 базовых цветов и способ окраски карточки — решение исполнителя.
- **Следствия:** нужна V19; без неё колокольчик отвечает 503 «нужны миграции V18 и V19», а сохранение цвета — ошибкой.
  **Исключение из правила «только семантические токены»:** цвет события — данные пользователя, хранится и выводится
  hex-значением (`style`), а не классом темы. Если сотрудник не открывает портал накануне, напоминания не будет —
  отправки «в фоне» (почта, push) нет. «Завтра» считается по часовому поясу процесса Go (на сервере не проверялось).
  Меню «⋮» с «Изменить» есть только в боковой панели дня (широкий экран); в выдвижной панели на узком экране его,
  как и «Удалить», не было и нет.

## ADR-052. Девблог: общий черновик в Markdown, публикация новостью, окошко при входе и уведомление всем

- **Статус:** действует с 2026-10-08
- **Решение:**
  - В меню профиля в роли администратора — «Редактировать девблог» (`/admin/devblog`, `requiresAdmin`). Отдельная
    страница, а не `USlideover`: две колонки (Markdown и предпросмотр) в боковую панель не помещаются.
  - **Один общий черновик** (`devblog_draft`, V20) с автосохранением и номером версии. Сохранение с устаревшей версией
    отвергается (409) — администратор выбирает «Взять сохранённую» или «Оставить мою»; молча чужая правка не
    затирается. Редактирования в реальном времени нет.
  - Markdown разбирает `UEditor` Nuxt UI (`content-type="markdown"`, расширение `@tiptap/markdown` — зависимость
    Nuxt UI): предпросмотр и HTML для публикации — из одного редактора, новых библиотек нет. HTML проходит через схему
    редактора, произвольная разметка из текста в новость не попадает.
  - Публикация (транзакция): новость категории «Девблог» с обложкой (своя или `public/devblog-cover.svg`) — дальше это
    обычная новость (лента, реакции, комментарии); уведомление `devblog` всем активным сотрудникам, кроме автора; черновик
    очищается.
  - Окошко (`DevblogWelcomeModal`) — **последний** опубликованный девблог, который сотрудник не закрыл; старые выпуски
    не догоняют. Внутри — текст, реакции, поле комментария. Закрыли — `devblog_dismissed`, уведомление прочитано.
  Код: `backend/internal/handlers/devblog.go`; `src/pages/Admin/DevblogPage.vue`, `src/components/DevblogWelcomeModal.vue`,
  `src/composables/useDevblog.ts`.
  - **Дополнено 2026-10-08 по просьбе владельца («помощники как в Obsidian»):** поле Markdown — `MarkdownEditor.vue`
    (панель форматирования, горячие клавиши, продолжение списков по Enter, вложенность по Tab, ссылка из вставленного
    адреса, счётчик слов) поверх обычного `UTextarea`; новых библиотек нет. Ссылка — Ctrl+Shift+K: Ctrl+K занят
    глобальным поиском (`App.vue`, перехват на `window`). Курсив — `_…_`, чтобы не путать с `**жирным**`.
  - **Дополнено 2026-10-08 по просьбе владельца:** поле «Версия» (V21, `release_version`): по умолчанию последняя
    опубликованная + 0.0.1 (первая — 1.0.0), правится вручную, формат «X.Y.Z», без версии опубликовать нельзя.
    Показывается под заголовком новости-девблога, в окошке и предпросмотре — основной цвет темы с переливом
    (`DevblogVersionBadge.vue`; без анимации при «уменьшить движение»). Страница новости берёт запись из общего
    списка, поэтому версию догружает отдельным `news.php?id=` только для категории «Девблог».
  - **Дополнено 2026-10-08:** обложка в окошке и в предпросмотре — между версией и текстом (`DevblogCover.vue`),
    целиком на размытой подложке, как фото на странице новости; раньше окошко обрезало её до 16:7, а предпросмотр
    не показывал. Место «между версией и текстом» выбрал исполнитель по просьбе владельца («выше всего текста либо
    между версией и основным текстом, реши сам»).
  - **Дополнено 2026-10-08 (просьба владельца):** девблоги — только в ленте рабочего стола и на своей странице; во
    вкладке «Новости» их нет (`news.php?excludeCategory=`, фильтр на сервере, чтобы не ломать постраничную подгрузку).
    Автор в ленте и колокольчике — «Разработчики портала», а не опубликовавший администратор. «По теме» — только
    новости той же категории (раньше при пустой категории подставлялись все новости, и девблог показывал обычные);
    «Предыдущая / Следующая» — внутри своего вида: девблоги между собой, новости без девблогов.
- **Причина (подтверждена):** просьба владельца 2026-10-08: девблог из меню роли администратора, «общая рабочая зона
  с md-разметкой», «опубликовать»; у всех — окошко при первом заходе (закрыть, реакция, комментарий), публикация как
  новость, уведомление всем независимо от подписок. Ответы владельца: Markdown слева, предпросмотр справа; обложка своя
  или стандартная; в окошке — текст, реакции, поле комментария; черновик — один общий (вариант 1, про редактирование в
  реальном времени — рассказать).
- **Следствия:** нужна V20 (после V17); без неё `devblog.php` отвечает 503, а колокольчик — «нужны миграции V18–V20».
  Новый эндпоинт — в `main.go`, nginx wave2 и Vite; на сервере — `reload nginx` (IMP-63). Новость девблога редактируется
  как обычная (HTML-редактор новостей), исходный Markdown остаётся в `devblog_posts` и обратно не синхронизируется.
  Уведомления создаются строкой на каждого активного сотрудника (на тестовой базе — 186). «Подписки на группы» пока нет —
  при её появлении девблог по-прежнему идёт всем. Совместная правка в реальном времени потребовала бы
  WebSocket-сервера синхронизации (Yjs) — не делалась.

## ADR-053. Фильтр мата в комментариях и на стене: публикация через задачу, слова под звёздочками

- **Статус:** действует с 2026-10-08
- **Решение:**
  - Проверка — только на сервере (`backend/internal/profanity/profanity.go`), список слов на фронте не дублируется.
    Слово читается в кириллицу несколькими способами: транслит (pizda, hui, blyad) и похожие латинские буквы
    (xyй, cyka, nизда), цифры и символы (е6ать, 3блан — «3» как «з» и как «е», ye60k, $ука), растянутые буквы
    (хууууй), слова через точки, дефисы и пробелы по букве (х.у.й, х у й). Строгость — «мат + грубые слова» (выбор
    владельца): матерные корни с производными плюс сука, мудак, гандон, пидор, шлюха, говно, мразь, чмо, дрочить;
    «блин», «жопа», «хрен», «дерьмо» пропускаются.
  - Корни, которые встречаются внутри обычных слов, ищутся только в начале слова, с приставкой или целой
    словоформой: «еб» — хлеб, небо, вебинар; «бля» — употреблять, корабля; «манд» — команда, мандарин; «сук» —
    сукно, барсука. Исключения — «застрахуй», «скипидар», «Ебург», eBay, job и т.п. Проверено тестами и
    прогоном ~52 тыс. слов (документация + новости портала) — ложных срабатываний не осталось.
  - Нашёлся мат — сервер не публикует, а отвечает 422 с `data.profanity = {token, question, masked}`
    (`handlers/profanity_gate.go`). Задача с целым ответом: значение функции, уравнение или композиция функций.
    Тот же текст, присланный с `challengeToken` + `challengeAnswer`, публикуется, но найденные слова скрыты: первая и
    последняя буква остаются (`х****й`). Сохраняется только скрытый вариант.
  - Токен не хранится: HMAC над пользователем, хешем текста, ответом и сроком (15 минут); ответа в токене нет. Ключ
    создаётся при старте API — после перезапуска открытые задачи не подходят, автор получает новую. Неверный ответ —
    новая задача; после 8 неверных подряд — 10 минут отказа (429), счётчик в памяти процесса.
  - Где действует: `news_comments.php` `create`/`update`, `profile_wall.php` `create`/`update`/`greet`. Фронт:
    `postWithProfanityGate` (`useProfanityGate.ts`) повторяет запрос с ответом; окно `ProfanityChallengeModal.vue` —
    одно на приложение (`App.vue`). Закрыли окно — `ProfanityCancelledError`, тоста нет, текст остаётся в поле.
- **Причина (подтверждена):** просьба владельца 2026-10-08 — «чтобы в комментарии и на стенку не писали маты», с
  транслитом и заменой букв. Механику выбрал владелец: опубликовать можно, только решив «генерируемую математическую
  функцию», и «часть мата все равно зацензурится звездочками».
- **Следствия:** обойти фильтр можно словами, которых нет в списке, или новыми способами записи — список правится в
  `profanity.go` вместе с `profanity_test.go`. Старые комментарии и записи не перепроверялись. Правка уже скрытого
  текста задачу не вызывает (звёздочки разбивают слово). Заголовки и текст новостей, девблог, формы и профиль
  фильтром не проверяются — только комментарии и стена.

## ADR-054. Мероприятия: время, место и лимит мест отдельными полями, список записавшихся — организаторам

- **Статус:** действует с 2026-10-13
- **Решение:**
  - В `events` — `time_start`, `time_end` (`'HH:MM'`, как в `calendar_entries`), `location`, `max_participants`
    (V22). Все необязательные: пусто — «Уточняется», лимита нет — «без ограничения». Раньше полей не было: время и
    место угадывались регулярными выражениями из описания. Для старых мероприятий без полей это поведение оставлено
    (афиша, календарь), новые берут поля.
  - Время вводится `UInputTime` с 24-часовым форматом (как в журнале отсутствия): «1300» — 13:00. Окончание без
    начала и окончание раньше начала сервер не принимает (422).
  - Лимит проверяется в `event_rsvp.php` в транзакции с `SELECT … FOR UPDATE` строки мероприятия: два одновременных
    «Записаться» на последнее место не пройдут оба. Мест нет — 409 «Мест больше нет», кнопка — «Мест нет».
    Отменить свою запись можно всегда. Лимит можно опустить ниже числа записавшихся: они остаются, новых не пускаем.
    Листа ожидания нет.
  - Кто записался — `GET event_rsvp.php?eventId=`, только с правом правки раздела «Мероприятия» (и администратору);
    на странице мероприятия — карточка «Записавшиеся» (ФИО, аватар, время записи, ссылка на профиль). Остальные
    видят только число: «Записалось 12 из 30».
- **Причина (подтверждена):** обратная связь сотрудника 2026-10-13, переданная владельцем: некуда внести место и
  время (карточка пишет «уточняется»), нет ограничения по количеству записей, не видно, кто записывается. Ответы
  владельца: список — только организаторам; при заполнении — запись закрыта (без листа ожидания).
- **Следствия:** нужна V22; без неё `events.php` и запись отвечают 503 с именем миграции, колокольчик — «нужны
  миграции V18–V22». Экспорта списка (Excel) нет. Подразделение участника в списке не показывается (в `user_info`
  только id ОФО).

## ADR-055. Мероприятия в календаре — только после записи; виджет «Мероприятия»; описание в редакторе новостей

- **Статус:** действует с 2026-10-14
- **Решение:**
  - Календарь (`useCalendarFeed`) показывает мероприятие, только если сотрудник на него записался. Раньше в
    календаре были все мероприятия, а записанные отмечались бейджем. Напоминание накануне и раньше было только
    по записи.
  - Новые мероприятия видны на рабочем столе в виджете «Мероприятия» (`HomeEventsWidget.vue`) — в том же виде,
    что «Календарь» и «Дни рождения коллег»: ближайшие предстоящие (`events.php?date_from=сегодня&order=date&dir=asc`),
    без бейджа «Архив», до 5. Нет предстоящих — виджета нет.
  - Описание мероприятия — тот же `UEditor`, что у новостей (HTML, панель, эмодзи, Markdown-сокращения при вводе),
    компонент `EventDescriptionEditor.vue`. Хранится HTML в `events.description`; миграции не нужно. Старые
    описания — обычный текст: показываются как текст (`whitespace-pre-line`), в редакторе открываются абзацами.
    Пустой редактор сохраняется как `null`.
- **Причина (подтверждена):** просьба владельца 2026-10-14: «новые мероприятия не должны сразу добавляться в
  календарь, только после записи», «должны появляться на главной в таком же виджете как и „Дни рождения“,
  „Календарь“», «в описании мероприятия должна быть мд разметка как в новостях».
- **Следствия:** HTML описания выводится через `v-html`, как у новостей: писать его могут только организаторы
  (раздел «Мероприятия»), отдельной санитизации на сервере нет — как и у новостей. Виджет и календарь грузят
  `events.php` каждый сам.

## ADR-056. Несколько времён у мероприятия, у каждого свой лимит; запись — на одно время

- **Статус:** действует с 2026-10-16
- **Решение:**
  - Время мероприятия — список (`event_slots`, V23): начало, окончание, лимит мест, порядок. Все времена — в день
    мероприятия; место — одно на мероприятие (`events.location`). У мероприятия всегда есть хотя бы одно время;
    пустое — «Время уточняется». Поля времени и лимита из V22 (`events.time_start/time_end/max_participants`)
    перенесены миграцией в первое время и больше не читаются (столбцы оставлены — откат безопасен).
  - Сотрудник записан на одно время мероприятия (`event_rsvps.slot_id`; PK `(event_id, user_id)` прежний). Выбор
    другого — перезапись: прежнее место освобождается. Лимит проверяется по времени под блокировкой его строки.
  - Форма: строки «Время N» (начало, окончание, лимит) и «+ Добавить время» под последней; новое время
    начинается с окончания предыдущего. Удаление времени, на которое записались, — через подтверждение: после
    сохранения записи на него удаляются (каскад).
  - Напоминание накануне, календарь и виджет «Мероприятия» показывают время, на которое записан сотрудник.
- **Причина (подтверждена):** просьба владельца 2026-10-16: «у одного мероприятия может быть несколько этапов и у
  людей должен быть выбор, куда записаться», «добавление дополнительного времени… через + под последним временем»,
  «пользователю напоминают про событие и время», «для каждого времени устанавливается ограничение записи». Ответы
  владельца: записаться можно только на одно время; все времена в один день; место — одно на мероприятие.
- **Следствия:** нужна V23 (после V22); без неё `events.php` и запись отвечают 503. Сотрудники, чьё время удалил
  организатор, теряют запись без уведомления. Листа ожидания по-прежнему нет. Старый код (до деплоя) на базе с
  V23 создаёт записи без времени — повторный прогон V23 при деплое относит их к первому времени.

## ADR-057. Сбой отправки теста не превращается в «0»

- **Статус:** действует с 2026-10-16
- **Решение:** `src/pages/Tests/TestRunner.vue`, `finalize()`. Если передан `submit` (тесты курса,
  `CourseTestPage.vue`; тест по ссылке, `TestLinkPage.vue`) и он завершился ошибкой, форма **не закрывается**:
  остаёмся на последнем вопросе, показывается `UAlert` «Ответы не отправлены» с текстом ошибки, повтор — той же
  кнопкой «Завершить». Локальная сессия (`clearSession`) очищается только после успешной отправки. Путь с
  `record` (`/tests`, `tests_submit.php`) не менялся: там клиент знает правильные ответы и показывает честный
  результат, даже если попытку не записали (например, лимит попыток).
- **Причина (подтверждена кодом):** раньше ошибка `submit` глоталась (`catch { recorded = false }`), а у тестов курса
  сервер вырезает `correct` (`StripCorrect`), поэтому клиентский разбор давал `scorable = 0` → `emitFinish` с
  `score = 0`. Пользователь видел «0» / «Тест завершён», а в админке попытка была `in_progress` и в результатах
  (только `completed`) не отображалась. Что именно упало у конкретного сотрудника, по коду не установлено.
- **Следствия:** если ответ сервера потерялся, а попытка уже завершилась, повтор получит «Попытка уже завершена»
  (409) — результат смотреть в админке. На сервере по-прежнему нет логирования запросов в Go-API.

## ADR-058. Повторное прохождение теста курса после «Закрыть» — новая попытка

- **Статус:** действует с 2026-10-23
- **Решение:** `src/pages/Courses/employee/CourseTestPage.vue`. Страница помнит, что текущая попытка завершена
  (`attemptDone` после успешного `attemptFinish`). Когда сотрудник снова нажимает «Пройти тест» (раннер шлёт новое
  событие `start`, `TestRunner.vue`), страница заводит новую попытку через `tests_attempt_start.php`; на случай,
  если событие не сработало, то же проверяется перед отправкой ответов. «Пройти ещё раз» работает как раньше
  (новая попытка + пересоздание раннера), лишних попыток не появляется.
- **Причина (подтверждена кодом и данными):** после проваленного теста экран результата советует «Закройте экран и
  попробуйте пройти тест снова». «Закрыть» возвращал раннер на «Пройти тест», но страница держала id уже
  завершённой попытки, и ответы уходили в неё: сервер отвечал 409 «Попытка уже завершена». До ADR-057 ошибка
  глоталась и показывался «0 из 0», с ADR-057 — «Ответы не отправлены»; пересдать нельзя было без ухода со
  страницы. Случай 2026-10-23: сотрудник (enrollment 127, тест 03) провалил попытку 1974 в 08:33, пересдать
  смог только после повторного входа на страницу (попытка 1981, 09:19–09:24, 85%).
- **Следствия:** время начала новой попытки — момент нажатия «Пройти тест». Лимит попыток проверяется при
  старте: исчерпан — тост «Не удалось начать новую попытку» и та же ошибка при отправке, ответы остаются в раннере.

## Как добавлять запись

1. Решение принято и **видно в коде** — иначе это не ADR, а предложение
   (ему место в [known-issues.md](known-issues.md)).
2. Укажите файл и строку.
3. Причину пишите только подтверждённую. Не уверены — `[НЕИЗВЕСТНО]`.
4. Опишите следствия: что теперь нельзя сделать или о чём нужно помнить.
5. Отменяя решение — не удаляйте запись, пометьте «отменено ADR-NNN».

## ADR-059. Админ добавляет подразделения ОФО из дашборда; «Дэшборд администратора» в меню — только в роли администратора

- **Статус:** действует с 2026-10-26
- **Решение:** `POST /api/ofo_tree.php` `{name, category_id, parent_id?}` (`handlers/ofo.go`, `requireAdmin`). Без
  `parent_id` — корень категории, с ним категория берётся у родителя. Кнопки «Добавить ОФО» (панель) и «Добавить» во
  вложенных (карточка подразделения) — `AdminOfoPanel.vue`. Тот же URL, что у GET, поэтому `main.go`, nginx и Vite не
  менялись. Пункт меню «Дэшборд администратора» (`AppHeader.vue`) показывается рядом с «Редактировать девблог» только
  при `currentRole === 'admin'`.
- **Причина (подтверждена):** просьба владельца 2026-10-26.
- **Следствия:** `id`/`unit_number` новой записи — из последовательности (если есть у `ofo_unit.id`) либо `MAX+1`;
  `level` = уровень родителя + 1 (у корня — как у существующих корней категории). Реальная продовая схема в
  репозитории неизвестна, на проде не проверялось. Нет переименования, переноса и удаления — не заказывалось.
